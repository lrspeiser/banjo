## Concrete reliability findings

1. **A command array is ordered partial execution.** `CreatorWorld::executeJson` catches each command error and continues. Earlier successful commands remain applied. This can be useful, but clients need an explicit contract; it is not an atomic multi-object transaction. Future assembly commits need a dedicated all-or-nothing operation. Top-level parse failures also travel through a different error path.
2. **CLI process success does not mean every command succeeded.** `creator_main.cpp` prints structured command results and returns zero even when a result contains `ok:false`. Document this now; choose an explicit exit-status policy for scripts while preserving individual results.
3. **Retry behavior differs across mutations.** Create/rebuild/reclaim compare stored request receipts in the new backend. `step` has no request ID and advances again if resent. A replayed creation can return an ID whose object was later reclaimed. Return the original operation receipt and distinguish historical outcome from current object existence; never resurrect it.
4. **Preview is a quote, not a reservation.** Creation rechecks resources and geometry, which protects correctness. Add proposal identity/content binding, relevant authoring/object revisions and a snapshot tick; recheck current placement and stock at acceptance. Object authoring revision is not simulation time: a body can move while that revision stays unchanged. Stale results should explain whether to inspect, re-preview or re-propose.
5. **In-memory commit and durable acknowledgement are separate.** The workshop creates first and saves afterward. A save failure can leave an accepted object in memory while the old file remains on disk. The existing temporary-file replacement is useful, but the API must define crash recovery and whether an acknowledgement is durable. Test disk-write failure and process interruption around publication before promising transaction durability.
6. **Observation is too coarse for another application.** `inspect` includes the entire serialized world/history; the assistant now prunes history, but clients lack filtered/paged queries and event cursors. `step` drains impacts without exposing them in the creator command surface. Add bounded snapshots and events carrying sequence/tick/object identity, plus an explicit resync path if history expires.

## Recommended implementation order

**First, finish the current lifecycle and command reliability boundary.** Connect and verify selected-object rebuild/reclaim, then standardize envelopes/errors, receipt lookup, retry semantics, durable acknowledgement and current-state revalidation. Preserve the existing compiler and single owner of mutations. Publish schemas and a small scripted client before adding a network service. These changes need no new constitutive law.

**Next, deliver the functional test loop with today's supported primitives.** Example intent: “Use my collected material to make a ball that travels at least two metres down this ramp from rest without leaving it.” The system records the distance, time limit, geometry/material constraints and tolerances; compiles and previews a candidate; runs a bounded test in an isolated snapshot; returns measured travel/slip/contact evidence; then accepts a material-accounted creation or revision. Follow with “Use less material and run the same test again.” Failed tests return observations rather than a success claim, and repeated model attempts have a fixed budget.

Run the same baseline dimensions, initial conditions, surface and numerics for glass, oak and iron. Resource-constrained redesigns may deliberately use different sizes, but report them as a separate comparison and retain the common baseline. Unsupported damage or rolling criteria must be reported as unsupported. Live-world inventory and time remain unchanged during speculative test runs; successful acceptance is a separate command. Save the specification, test declaration, starting state, metrics and runtime versions, and rerun without an LLM.

**Then add interaction and the first assembly through that same contract.** Add physical actions and events, then a constrained lever or wheel/axle as a small mechanism. The assembly must expose measurable motion and reaction loads and derive its mass/inertia from allocated parts. General custom laws, damage-aware salvage, large-world streaming, marketplace/economy and multiplayer come later under the existing gates. This order keeps the application visible without hiding unresolved conservation, material realism or performance work.

## Proposed acceptance contract, not implemented operation names

The API should let a client express `describe capabilities → inspect world/resources → propose design and test → compile/preview → run isolated test → inspect result → commit → act/observe → revise/reclaim → checkpoint/export`. Whether these travel over an embedded call, standard input or HTTP is an adapter choice.

Each mutation should identify the API version, request and world, operation, expected relevant revision and typed arguments. Each result should identify the operation, accepted revision/tick, lifecycle/durability status, warnings/approximations and either data or a stable error code with field-level details. Long jobs additionally need status/cancellation/result identity. Tests and actions must state units, coordinate frames, limits and physical work sources. Capability/version mismatch must fail explicitly instead of silently changing a material law.

Completion of this milestone means a client can create, measure, revise and reload a working supported object through these interfaces without manual JSON repair, duplicate resource use or a mandatory new LLM call. It does not mean the full engine or publishing goal is complete.
